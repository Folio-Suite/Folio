# Apple and macOS agent skills: a small portfolio for Folio

Research snapshot: **26 September 2026**. This is a source audit and adoption recommendation, not an installation or a benchmark of agent performance. No candidate skill was installed or executed, and no application configuration changed.

## Recommendation

For Folio, start with **Apple's applicable Xcode skills and a narrowly scoped AppKit accessibility pilot**. Add **AvdLee's Core Data skill** for persistence work after correcting its conflict-policy guidance. Keep **selected Axiom references** available for AppKit modernization, TextKit, and distribution questions. Add Swift Concurrency only when a concrete Swift boundary needs it. A general SwiftUI bundle does not address Folio's central needs.

This ranking follows Folio's adopted direction: Objective-C, AppKit, storyboard-authored interfaces, visually authored Core Data, public domain Kits, native Xcode tests, and coordinated Suite distribution. Swift earns its place through a concrete benefit. These are current project requirements, not omissions to modernize away. [ADR 0009](../adr/0009-continue-cocoa-suite-with-domain-kits.md), [contributor requirements](../../CONTRIBUTING.md).

For a **SwiftUI macOS project**, choose one primary SwiftUI specialist: AvdLee for broader current macOS coverage and profiling workflows, or Paul Hudson's smaller `swiftui-pro` for focused code reviews. Supplement it with concurrency or macOS references only when needed. Installing both by default adds overlapping rules without demonstrated benefit.

The immediate Folio shortlist is deliberately small:

1. **First: applicable Apple skills**, discovered from the installed Xcode resources, especially compiler diagnostics and targeted accessibility. Keep the existing Xcode connection.
2. **Second: rgmez's AppKit accessibility auditor**, piloted on one editor workflow with actual keyboard and VoiceOver checks.
3. **Third: AvdLee Core Data**, only after the conflict-policy overstatement is corrected or explicitly overridden in the pilot scope.

Axiom remains a reference shelf until its selected instructions are checked and constrained. Neither it nor Core Data should be installed unchanged as an authoritative global policy. The conditional Swift Concurrency and SwiftUI choices belong to tasks that use those technologies; their existence is not a reason to introduce them. This leaves room for a future local Cocoa workflow without accumulating overlapping broad triggers now.

## What the source audit found

### Apple: real portable skills, plus separate tool access

Apple explicitly supports exporting Xcode's skills for other agent workflows with `xcrun agent skills export`. This is first-party guidance, not merely a community repository claiming Apple expertise. [WWDC26: Modernize your UIKit app, agentic coding section](https://developer.apple.com/videos/play/wwdc2026/278/?time=847).

Fifteen skills were already present in this machine's Xcode-specific Codex configuration. The most relevant sampled files are `audit-xcode-security-settings`, `accessibility-voiceover-specialist`, and `accessibility-sufficient-contrast-specialist`. The security audit covers Objective-C diagnostics and hardening but explicitly excludes signing, privacy, and networking. The accessibility files include AppKit APIs; contrast permits unresolved findings to remain unverified. The VoiceOver skill's source-only binary verdict must not become a claim of complete runtime accessibility. These are local, version-specific observations, not a promise that every Codex installation discovers them. [Local security skill](/Users/ctwelve/Library/Developer/Xcode/CodingAssistant/codex/skills/__xcode/audit-xcode-security-settings/SKILL.md), [VoiceOver skill](/Users/ctwelve/Library/Developer/Xcode/CodingAssistant/codex/skills/__xcode/accessibility-voiceover-specialist/SKILL.md), [contrast skill](/Users/ctwelve/Library/Developer/Xcode/CodingAssistant/codex/skills/__xcode/accessibility-sufficient-contrast-specialist/SKILL.md).

Apple's document-based skill targets the new SDK 27 **SwiftUI** document protocols; it does not fill the NSDocument gap. Its test-modernization skill favors Swift Testing where possible, so it is not a default migration instruction for Folio's Objective-C tests. The packaged translation skill handles requested locale/key translation, not Folio's full localization boundary. [Local document skill](/Users/ctwelve/Library/Developer/Xcode/CodingAssistant/codex/skills/__xcode/building-document-based-swiftui-applications/SKILL.md), [test skill](/Users/ctwelve/Library/Developer/Xcode/CodingAssistant/codex/skills/__xcode/modernize-tests/SKILL.md), [Folio localization](../localization.md).

A skill supplies instructions and references; an MCP connection supplies callable capabilities. The existing session already exposes Xcode build/test/debug/localization tools, and a read-only DocumentationSearch query successfully retrieved NSDocument guidance. Installing another Xcode MCP is not necessary to gain that access. Apple's external-agent bridge and its Xcode-specific agent configuration are distinct from portable skill discovery. [External access](https://developer.apple.com/documentation/xcode/giving-external-agents-access-to-xcode), [agent customization](https://developer.apple.com/documentation/xcode/extending-and-customizing-agents).

### Focused AppKit accessibility: the best small third-party pilot

The rgmez `appkit-accessibility-auditor` directly addresses NSView, NSWindowController, NSTableView, NSOutlineView, key-view loops, roles/actions/notifications, long-form text, and continuous reading. It requests localized changes and concrete manual verification rather than architectural replacement. Its separate checklist makes acceptance reviewable. This is a particularly good fit for Write's editor and Manuscript sidebar. Its generic left-to-right reading-order advice still needs localization judgment. [Skill](https://github.com/rgmez/apple-accessibility-skills/blob/ab6f67852f5da2b76dbfa2574451269e9386b2a8/skills/appkit-accessibility-auditor/SKILL.md), [manual checklist](https://github.com/rgmez/apple-accessibility-skills/blob/ab6f67852f5da2b76dbfa2574451269e9386b2a8/skills/appkit-accessibility-auditor/checklist.md).

Treat this as a pilot, not an established quality guarantee. Its narrow trigger is an advantage over broad Apple bundles. Avoid simultaneously running several accessibility reviewers with overlapping output contracts unless comparing their findings deliberately.

### Core Data and concurrency: useful triage, not product policy

AvdLee's Core Data entry point asks for the store, context, deployment target, and diagnostic, then routes into migrations, history, batching, threading, and testing. Its model reference explicitly uses Xcode's model editor, which fits Folio. Its threading reference emphasizes context confinement and object-ID handoff; translate examples into the owning Objective-C adapter rather than exposing managed objects through Kit APIs. [Skill](https://github.com/AvdLee/Core-Data-Agent-Skill/blob/855ca7d0df50e82b00c12881dd9cd23c19ef5f49/core-data-expert/SKILL.md), [threading](https://github.com/AvdLee/Core-Data-Agent-Skill/blob/855ca7d0df50e82b00c12881dd9cd23c19ef5f49/core-data-expert/references/threading.md).

One material correction is required: the model guide prescribes store-trump merging and says constraint violations otherwise crash. Apple's default error policy instead permits a failed save to report conflicts. Choosing which user's changes win is a domain decision, not a universal safety fix. Preserve Folio's conflict semantics. [Problematic reference](https://github.com/AvdLee/Core-Data-Agent-Skill/blob/855ca7d0df50e82b00c12881dd9cd23c19ef5f49/core-data-expert/references/model-configuration.md#required-merge-policy), [Apple NSMergePolicy.error](https://developer.apple.com/documentation/coredata/nsmergepolicy/error).

The Swift Concurrency skill's strongest feature is its requirement to inspect actual language mode, default isolation, and strict-concurrency settings before diagnosis. It favors small changes and rejects blanket MainActor fixes. Its references discuss both object-ID transfer and optional value snapshots, including the cost of introducing another abstraction. Use it only for Swift code or a specific language boundary; do not turn a Cocoa queue-confinement issue into a Suite rewrite. Examples remain subject to compilation and lifecycle testing. [Skill](https://github.com/AvdLee/Swift-Concurrency-Agent-Skill/blob/d5770817d2622e1585b1f7eaebc791a9cb0959c8/skills/swift-concurrency/SKILL.md), [Core Data integration](https://github.com/AvdLee/Swift-Concurrency-Agent-Skill/blob/d5770817d2622e1585b1f7eaebc791a9cb0959c8/skills/swift-concurrency/references/core-data.md).

### Axiom: valuable breadth with uneven correctness

The canonical repository is **CharlesWiltgen/Axiom**. Its actual Codex distribution includes an `axiom-macos` router, not just iOS material. AppKit modernization covers native keyboard navigation and state restoration; TextKit references cover NSTextView opt-in and compatibility-mode hazards despite living under the UIKit suite. The distribution reference distinguishes nested signing order, notarization, packaging, and Sparkle, including avoiding `--deep` when signing. These are useful lookup materials. [macOS router](https://github.com/CharlesWiltgen/Axiom/blob/c297598480e39d992044831ac0b895a431c7db51/axiom-codex/skills/axiom-macos/SKILL.md), [AppKit modernization](https://github.com/CharlesWiltgen/Axiom/blob/c297598480e39d992044831ac0b895a431c7db51/axiom-codex/skills/axiom-macos/skills/appkit-modernization.md), [TextKit](https://github.com/CharlesWiltgen/Axiom/blob/c297598480e39d992044831ac0b895a431c7db51/axiom-codex/skills/axiom-uikit/skills/textkit-ref.md), [distribution](https://github.com/CharlesWiltgen/Axiom/blob/c297598480e39d992044831ac0b895a431c7db51/axiom-codex/skills/axiom-macos/skills/direct-distribution.md).

However, its sandbox reference repeatedly asserts that Xcode Debug builds bypass sandboxing and have unrestricted disk access, and that an exported app will be sandboxed. Build configuration alone establishes neither. Apple states that new macOS apps receive the sandbox entitlement, describes entitlement-based configuration, and explicitly verifies sandboxed apps launched from Xcode. This incorrect generalization rules out treating the bundle as authoritative. [Axiom sandbox reference](https://github.com/CharlesWiltgen/Axiom/blob/c297598480e39d992044831ac0b895a431c7db51/axiom-codex/skills/axiom-macos/skills/sandbox-and-file-access.md#why-debug-builds-bypass-it), [Apple defaults](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox), [Apple configuration](https://developer.apple.com/documentation/xcode/configuring-the-macos-app-sandbox).

The router also demands activation for essentially every macOS task and routes many ordinary concerns into SwiftUI. Prefer explicit, selected references, checking OS 27 additions against Folio's macOS 26.5 minimum. Do not let broad triggers replace repository architecture, packaging, or test workflows.

### The two user examples and the SwiftUI alternative

Paul Hudson's `swiftui-pro` is a compact review workflow with topic-based references, project-convention awareness, and a useful prohibition on invented findings. Its actual instructions nevertheless default new apps to iOS 26, prefer Swift 6.2+, and discourage UIKit. The design reference's 44-point target rule is explicitly iOS guidance. Good SwiftUI review material does not automatically constitute desktop Cocoa expertise. [Skill](https://github.com/twostraws/SwiftUI-Agent-Skill/blob/be297ff80dddec529af1f9b1f1f114aab6c9d11c/swiftui-pro/SKILL.md), [design](https://github.com/twostraws/SwiftUI-Agent-Skill/blob/be297ff80dddec529af1f9b1f1f114aab6c9d11c/swiftui-pro/references/design.md).

AvdLee's SwiftUI alternative includes explicit macOS scenes, views, window styling, localization, and trace-analysis workflows. It avoids mandating MVVM and distinguishes hard from soft deprecation. Its document reference separates SDK 27 protocols from earlier deployment targets. This makes it the broader current choice for a SwiftUI Mac project, while its SwiftUI-first bridging policy remains inappropriate as Folio's default. [Skill](https://github.com/AvdLee/SwiftUI-Agent-Skill/blob/b24e68a965dc4b5bd2cc41dc60c094a26a9379ce/skills/swiftui-expert-skill/SKILL.md), [macOS scenes](https://github.com/AvdLee/SwiftUI-Agent-Skill/blob/b24e68a965dc4b5bd2cc41dc60c094a26a9379ce/skills/swiftui-expert-skill/references/macos-scenes.md).

Fayazara's six skills are concrete recipes for building, settings, Sparkle, native patterns, notch overlays, and releases. The sample settings controller creates its interface in code and hosts SwiftUI; the updater demonstrates a KVO/Combine bridge. These can help a small SwiftUI utility, but do not provide storyboard, public-Kit, or NSDocument architecture guidance. [Settings sample](https://github.com/fayazara/macos-app-skills/blob/a60365ae85bfc3d1f2f8b260b080d77bfb2f3ec0/settings-ui/references/SettingsWindowController.swift), [updater sample](https://github.com/fayazara/macos-app-skills/blob/a60365ae85bfc3d1f2f8b260b080d77bfb2f3ec0/auto-update/references/UpdaterManager.swift).

Its build recipe filters output through a shell pipeline, so the pipeline's status is not reliable build-success evidence without additional handling. Its release skill combines version changes, DMG/Sparkle, push, and GitHub publication, and broad distribution keywords trigger the whole workflow. Folio already has a governed Ruby installer pipeline; this is not a suitable drop-in release skill. [Build](https://github.com/fayazara/macos-app-skills/blob/a60365ae85bfc3d1f2f8b260b080d77bfb2f3ec0/build/SKILL.md), [release](https://github.com/fayazara/macos-app-skills/blob/a60365ae85bfc3d1f2f8b260b080d77bfb2f3ec0/release/SKILL.md), [Suite installer](../installer.md).

Bart Reardon's Mac behavior skill adds an unusually useful manual rubric for commands, selection, drag/drop, pasteboard, state, and multiwindow behavior. However, its substrate-selection step expressly prefers SwiftUI and AppKit only as a targeted fallback. Use its behavioral questions as reference material, not its architecture instruction. [Skill](https://github.com/bartreardon/skills/blob/c4e550d3411eb4dd30310592394c7ec4ac90f81e/mac-arsed-mac-app/SKILL.md), [QA rubric](https://github.com/bartreardon/skills/blob/c4e550d3411eb4dd30310592394c7ec4ac90f81e/mac-arsed-mac-app/reference/review-and-qa.md).

## Remaining gaps and adoption conditions

No audited candidate provides a complete Folio-oriented workflow for **NSDocument/autosave/Versions; responder-chain command validation; NSTextView/TextKit with undo; Objective-C/KVC/KVO; visually versioned Core Data; framework localization; or Suite signing, shared-framework installation, and XPC lifecycle**. Individual references cover pieces. This is an audit boundary, not a claim that no such skill exists anywhere.

The existing repository skills cover general engineering processes. The most valuable eventual local addition would connect those processes to Folio's Cocoa contracts and the already available Xcode tools, using current Apple sources for NSDocument, NSResponder, AppKit accessibility, and Core Data. It should preserve authored Work content during localization and distinguish an unsigned build, signed native tests, and clean-install proof. [NSDocument](https://developer.apple.com/documentation/appkit/nsdocument), [NSResponder](https://developer.apple.com/documentation/appkit/nsresponder), [AppKit accessibility](https://developer.apple.com/documentation/appkit/accessibility), [Folio validation](../../CONTRIBUTING.md#validation).

Pilot one bounded task per candidate: an accessibility review of the editor, a Core Data context/migration diagnosis, and an AppKit/TextKit issue. Record useful findings, false positives, API verification, and native results. Pin the inspected revision, retain upstream notices, narrow triggers, and re-audit updates. Keep only skills that improve those outcomes; source reputation, stars, and the number of references are insufficient evidence by themselves.
